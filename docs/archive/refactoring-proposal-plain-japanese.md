# ソフトウェアの内部整理（リファクタリング）のご提案

**〜 プログラミングの知識がなくてもわかる解説 〜**

- 作成日: 2026-07-27
- 対象: JavaTextEditor（Vim と Emacs の良いところを統合したテキストエディタ）
- この文書の目的: これから行う「内部の整理整頓」が、なぜ必要で、なぜこのやり方が正しいのかを、専門用語なしでご説明すること

---

## 1. 一言でいうと

**建物の外観も使い勝手も一切変えずに、内部の間取りを整理します。**

お客様が画面で見るもの、操作の手順、動く速さ — これらは何ひとつ変わりません。
変わるのは「今後、新しい機能を追加したり不具合を直したりするときの、作業のしやすさ」だけです。

---

## 2. 今、何が起きているのか

### たとえ話：優秀な工房の「なんでも作業台」

このソフトウェアを工房にたとえます。

工房そのものは、とてもよくできています。道具（部品）は種類ごとに棚に整理され、
製品の品質を確かめる検査工程（テスト）も、製品本体より手厚く用意されています。

問題はひとつだけ。**工房の真ん中に「なんでも作業台」が1台あり、あらゆる作業がそこに集中している**ことです。

- 材料の加工も、この台の上
- お客様からの注文の受付も、この台の上
- 完成品の見た目の仕上げも、この台の上
- 他の職人への指示出しも、この台の上

一人の熟練職人が全部を一台でこなしているので、**今は問題なく回っています**。
しかし作業台の上は年々ものが増え、今や全体の3分の1がこの一台に載っている状態です。

### 実際の数字

| 項目 | 実測値 |
|---|---|
| ソフトウェア全体 | 約21,000行 |
| そのうち「なんでも作業台」にあたる1つのファイル | **約6,800行（全体の32%）** |
| そのファイルが手を伸ばしている棚の数 | **15棚のうち14棚** |
| そのファイルが持つ「外部への連絡手段」 | 18種類（その都度追加されたもの） |

15ある棚のうち14に手を伸ばしている、という点が問題の核心です。
**このファイルを触るたびに、ソフトウェアのほぼ全機能に影響が及ぶ可能性がある**ということだからです。

### 何が困るのか（お客様に関係のある形で）

1. **新機能の追加が、だんだん遅くなります。**
   作業台に新しい仕事を1つ載せるたびに、既に載っている仕事すべてとぶつからないか確認が必要になります。

2. **1つの修正が、無関係な場所を壊すリスクがあります。**
   全部が1か所に集まっているため、影響範囲が読みにくくなります。

3. **担当者の引き継ぎが難しくなります。**
   「この一台の上で何が起きているか」を理解するのに時間がかかります。

**今すぐ壊れるという話ではありません。** 今のうちに手を打つべき、という予防保全のご提案です。

## 3. ご提案する2つの整理

### 整理その1：「モジュラーモノリス」＝ 部屋の役割と入口をはっきりさせる

聞き慣れない言葉ですが、意味はシンプルです。

> **建物は1棟のまま。ただし、部屋ごとの役割と「正式な入口」をはっきり決める。**

大事なのは「**建物を分けるわけではない**」という点です。

近年よく聞く「マイクロサービス」という手法は、建物を複数のビルに分割する考え方です。
大人数のチームで開発する大規模なウェブサービスには向いていますが、
このソフトウェアのように**1台のパソコンで動く1本のアプリ**には過剰であり、
むしろ動作が遅く・複雑になります。**今回はその道は選びません。**

モジュラーモノリスは、その中間です。
建物は1棟のまま（＝今まで通り速く、シンプルに動く）で、
中の部屋割りだけをきちんとする、という現実的なやり方です。

具体的には、各部屋に「**この窓口だけを使ってください**」という正式な受付を1つ設けます。
今は部屋の中身が全部外から丸見えで、どこからでも直接手を突っ込める状態になっています。

#### ここが重要：この工事は、実はもう8割終わっています

今回の調査で、ソフトウェア内部の部屋のつながり方を全件洗い出しました。
その結果、**部屋どうしの依存関係に「堂々巡り」が1件もない**ことが確認できました。

これは非常に良い状態です。
（堂々巡りとは「A室はB室がないと動かず、B室はA室がないと動かない」という、
ほどけない絡まりのことです。これがあると、整理はとても困難になります。）

つまり今回の作業は、**ゼロから作り直すのではなく、すでに良い形になっている構造を仕上げるだけ**です。
これによって、作業期間もリスクも当初想定より大きく下がります。

### 整理その2：「MVP」＝ 中身・受付・見た目の3役に分ける

こちらも意味はシンプルです。飲食店にたとえます。

| 役割 | お店でいうと | ソフトでいうと |
|---|---|---|
| **中身（Model）** | 厨房。実際に料理を作る | 文章データそのもの、編集の実行 |
| **受付（Presenter）** | ホール係。注文を聞いて厨房に伝え、料理を客席へ運ぶ | キー入力を解釈し、結果を画面に渡す |
| **見た目（View）** | 客席とお皿。出されたものを並べるだけ | 画面表示。自分では何も判断しない |

今は、この3役を1人が兼任しています。だから作業台が混み合っているのです。
これを3人に分けます。

分けることの一番の効果は、**「厨房だけを、客席なしで検査できる」**ようになることです。
料理の味見をするのに、いちいち客席にお皿を並べる必要がなくなります。
＝ 品質チェックが速く、確実になります。

## 4. なぜこの方針が「適切」だと言えるのか

技術者の判断根拠を、4つに絞ってご説明します。

### 根拠1：今の作りに逆らわない

前述のとおり、部屋の絡まり（堂々巡り）がゼロでした。
また「受付が厨房から客席へ一方通行で運ぶ」という形も、実は**すでに半分できています**。

つまりこの提案は、**今の作りが向かっている方向に、あと一押しするだけ**です。
現状を否定して別のやり方に乗り換える提案ではありません。

> **補足：似た手法の中から「MVP」を選んだ理由**
>
> よく似た手法に「MVC」というものがあり、当初はそちらも候補でした。
> しかし調査の結果、MVCを選ぶと「客席が厨房を直接のぞきに行く」形になり、
> **せっかくゼロだった部屋の絡まりを、こちらから作り出してしまう**ことが分かりました。
> そのため、今の作りと矛盾しない「MVP」を選びます。
> これは今回の調査で判明した、方針上のもっとも重要な修正点です。

### 根拠2：品質チェックの仕組みを壊さずに済む

このソフトウェアには **97種類・約23,000行分の自動検査**が用意されています。
（製品本体が21,000行なので、**製品より検査のほうが分量が多い**ことになります。これは非常に健全な状態です。）

内部を作り替えるとき、最大の危険は「気づかないうちに何かを壊すこと」です。
しかしこのソフトウェアには、その危険を検知する仕組みが最初から手厚く備わっています。

さらに重要なのは、**この97種類の検査が、すでに「厨房だけを客席なしで検査する」やり方で書かれている**ことです。
今回の方針は、この既存の検査資産をそのまま活かせます。
（先ほど述べたMVCを選んでいた場合、この資産の多くが作り直しになるところでした。）

### 根拠3：この製品の性格に合っている

このソフトウェアには、開発当初から明確な方針があります。

- 外部の便利な部品を一切使わない（すべて自前で作る）
- 仕組みを学ぶことも目的のひとつなので、複雑な自動化に頼らない

モジュラーモノリスとMVPは、**どちらも特別な道具を必要としません**。
考え方と規律だけで実現できる整理術です。この製品の方針と正面から一致します。

逆に、DIコンテナ・イベントバスといった「便利だが仕組みが見えにくくなる道具」は、
今回**あえて使いません**。整理したはずが逆に読みにくくなっては本末転倒だからです。

### 根拠4：作業の進め方が既に実証済み

このソフトウェアでは、過去に**8回**、同種の内部整理を実施しています。
そのすべてで、以下の手順が守られてきました。

1. 作業前に、97種類の検査すべての結果を記録する
2. 1回の整理につき1件だけ変更し、その都度検査する
3. 完了時、**検査結果が作業前と1文字も違わないこと**を機械的に照合する

この8回はいずれも不具合ゼロで完了しています。
**やり方が確立していて、実績もある。** これが最大の安心材料です。

## 5. なぜ「いっそ全部作り直す」ではないのか

「そんなに整理が必要なら、いっそ最初から作り直したほうが早いのでは」というご意見はもっともです。
しかし今回は、**明確に反対**します。理由は3つです。

1. **今、正常に動いているものを止めることになります。**
   作り直しの期間中、新機能の追加も不具合修正も止まります。

2. **今動いている「見えない正しさ」が失われます。**
   長年の運用で積み上がった細かな挙動の調整は、仕様書には書かれていません。
   作り直すと、それらが静かに失われます。

3. **そもそも土台が良いので、必要ありません。**
   調査の結果、構造の土台はすでに健全でした。建て替えではなく、内装の整理で十分です。

**今回やるのは、住みながらの部屋の片付けです。**
一日の終わりには必ず、いつも通り住める状態に戻します。

## 6. 整理によって得られること

| 得られること | 具体的には |
|---|---|
| **新機能の追加が速くなる** | 触る範囲が「その部屋だけ」に限定され、全体への影響確認が不要になる |
| **不具合が減る** | 部屋の壁が影響の広がりを止める。1つの修正が無関係な場所を壊しにくくなる |
| **検査が速くなる** | 「厨房だけ」を客席なしで検査できるようになる |
| **引き継ぎやすくなる** | 担当者が代わっても、関係する部屋だけを読めばよくなる |
| **拡張機能が使えるようになる** | 実は既に作ってあるものの、現在つながっていない拡張の仕組みが、この整理で接続できるようになる |

## 7. 正直に申し上げておくこと

信頼していただくために、**この整理で得られないもの**も明記します。

1. **動作は速くなりません。**
   速度改善は別途、過去に実施済みです（大きなファイルの表示は当時256倍高速化しました）。
   今回は速度の話ではなく、**将来の開発しやすさへの投資**です。

2. **画面の見た目も操作方法も、一切変わりません。**
   お客様から見て「何も変わっていない」のが成功の状態です。

3. **一度では終わりません。**
   安全のため、小さく分けて何度かに分けて進めます。一気にやるのが最も危険だからです。

4. **既知の未解決事項3件には、今回は手をつけません。**
   これらは「どちらの動作が正しいか」の仕様判断が必要な項目で、技術的な整理とは別問題です。
   整理のついでに勝手に判断すると、意図しない仕様変更になってしまいます。
   別途、ご相談させてください。

## 8. 進め方

各段階の終わりには、**必ず「いつも通り動く状態」に戻します**。
途中で中断しても、そこまでの成果は無駄になりません。

| 段階 | 内容 | 完了の判定基準 |
|---|---|---|
| 準備 | 97種類の検査を全実行し、現状を記録する | 記録の取得 |
| 第1段階 | 各部屋の「正式な入口」を決める | 検査結果が準備段階と完全一致 |
| 第2段階 | 「なんでも作業台」から、中身（厨房）の役割を切り出す | 同上 |
| 第3段階 | 受付と見た目の役割を分離する | 同上 |
| 第4段階 | 部屋の壁が守られているかを自動確認する仕組みを追加する | 同上 |

各段階の完了条件はすべて同じ、**「検査結果が作業前と1文字も違わないこと」**です。
これを機械的に照合するため、「たぶん大丈夫」という判断は入りません。

## 9. まとめ

- ご提案の方針（モジュラーモノリス ＋ MVC/MVP）は、**適切です**
- ただし MVC ではなく **MVP を選ぶべき**です（MVCは今の良い構造を壊すため）
- 構造の土台はすでに健全で、この工事は**ゼロからではなく仕上げ**にあたります
- 97種類の自動検査が安全網として機能し、8回の実績ある手順で進められます
- 見た目・操作・速度は変わりません。変わるのは**今後の開発しやすさ**です
